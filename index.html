CALIPER

A verification layer for LLM-generated CAD geometry — measured before it is trusted.

Abstract

Large language models can now generate parametric CAD code and triangulated mesh geometry directly from natural-language descriptions, including dimensioned features such as threaded fits toleranced to tenths of a millimeter. What is missing is not generation capability but an independent, deterministic layer that verifies a generated geometry against its stated specification before that geometry is trusted — for slicing, for manufacturing, or for reuse. CALIPER is a proposed architecture for that verification layer: a structured specification format, a geometric and parametric checker, and a ground-truth dataset built from physically measured outcomes — designed to sit between any generation model, cloud or local, and any downstream manufacturing step. The pipeline is structured as composable nodes with feature-specific presets rather than a monolithic script. This repository currently contains the architecture design and a set of open questions, not a working implementation.

01

Motivation

Precision mechanical design — threaded fits, press fits, clearances specified to tenths of a millimeter — has traditionally required either a trained CAD operator or a dedicated CAM/CAE toolchain. A separate and largely undocumented practice has emerged around general-purpose LLMs: prompting them with detailed geometric and dimensional descriptions to generate mesh or parametric geometry, then slicing and 3D printing it directly, with tolerances tight enough for functional mechanical fits.

This works, some of the time, on some models. It is not yet a method with a name, a benchmark, or a way to know in advance whether a given prompt will succeed. There is currently no widely available tool that:

  • translates a natural-language dimensional specification into a structured, unambiguous form — tolerance type, nominal value, measurement convention;
  • checks a generated geometry against that specification before it is sliced;
  • records the physically measured outcome as ground truth, strictly downstream of any simulated or purely geometric check;
  • uses that ground truth to inform future generations, rather than starting from an unconditioned prompt every time.
02

Limitations of cloud LLMs, today

Cloud-hosted general-purpose models are, at present, the only widely available models capable of the geometric reasoning this task requires. Relying on them for a precision-dependent workflow introduces failure modes outside the control of the person using them — none specific to one vendor, all structural to the category:

  • Silent model drift — a provider can update weights or behavior at any time; the same prompt can silently produce a different result, with no version pin available to the end user.
  • Increasing conversational abstraction — as models are tuned toward general-purpose, safety-conscious use, literal numerical instructions appear more likely to be paraphrased or "helpfully" reinterpreted — the opposite of what a tolerance-critical task requires.
  • No first-class geometric verification — a language model can be asked to check its own output, but it is not a deterministic geometric kernel; that is not equivalent to measuring it.
  • No persistent, addressable memory of what worked — each session starts over; nothing surfaces "this exact feature was already solved" before generating from scratch.
03

Approach

The design separates concerns into a sequenced pipeline. Full detail in docs/architecture.md.

  1. Specification normalizationnatural language → structured, human-confirmed JSON, decoding constrained to schema where automated
  2. Generationcloud or local model, swappable; temperature fixed at 0 for feasibility testing — reproducibility, not accuracy
  3. Verificationdeterministic, non-LLM — not a second model grading the first, but a script or a physical measurement
  4. Slicing & printingfixed, versioned parameters
  5. Physical validationsole source of ground truth — not substitutable by simulation
  6. Frozen datasetrecorded only after physical measurement — successes and failures alike
  7. Retrievalnew prompts checked against validated cases before generation
  8. Fine-tuningfuture, conditional on dataset size — not a starting point
04

Execution model: nodes and presets

Each pipeline stage is, in practice, a node — typed input, typed output, independently testable, replaceable without touching the others. Cloud and local generation, for instance, are two implementations of the same node. A preset is a ready-made configuration for a recurring mechanical feature class — ISO metric thread, press fit, snap fit — pre-filling the specification schema and default tolerance convention for that feature.

Three ways to execute this pipeline were considered: a custom workflow/graph engine; reusing an existing automation platform such as n8n via a custom node package; or a lightweight declarative runner with no graph UI. The project starts with the declarative runner — lowest cost, testable immediately — while designing node boundaries clean enough to become an n8n node package later, without promising a graph interface that does not exist yet.

05

What this is not

  • Not a new CAD generation model — intended to sit in front of existing ones, cloud or open-source, indifferent to which is used.
  • Not a claim that any specific small open-weight model can currently replace large cloud models for this task — that is an open, untested question.
  • Not a production tool. At this stage: an architecture and a set of falsifiable open questions.
06

Open questions

  1. Does a specification-to-geometry pipeline actually require a large general-purpose LLM, or is the geometric reasoning narrow enough for a small, task-specific model once enough ground-truth data exists?
  2. Can a deterministic verifier catch failure modes that matter physically — e.g. interference on a helical thread — from mesh alone, without parametric or B-rep data?
  3. How much physically-measured data is "enough" before retrieval-based grounding meaningfully changes generation quality?
  4. Is tolerance-specification ambiguity better resolved by a stricter input format, an interactive confirmation step, or both together?
  5. Does this approach generalize beyond threaded mechanical fits, or does each feature class require its own verification logic?

No answers are asserted here. Contributions that answer, partially answer, or sharpen any of these are the most useful kind this project can receive right now.
